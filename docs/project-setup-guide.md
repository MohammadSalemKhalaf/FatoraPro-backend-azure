# Project Setup Guide: Bootstrapping a Flutter Frontend + ASP.NET Backend This Way

This document extracts a **general, reusable project-skeleton pattern** from a real, shipped
production codebase (a Flutter mobile app talking to an ASP.NET Core Web API, offline-first,
multi-tenant). It is written for an AI coding assistant or senior engineer starting a **brand new,
unrelated project** who wants to reproduce the same clean starting shape before writing the first
feature.

Everywhere a concrete example is given (`Customer`, `Order`, `Product`, `Fatora.API`, `lib/features/customers`),
treat the entity/project name as a placeholder for *your own domain*. The pattern being illustrated
is "a paginated list feature with offline cache and sync," not "a customers screen."

---

## 1. Flutter project skeleton

Create this folder tree **before** any feature code exists. Everything under `lib/` other than
`main.dart` and `bootstrap.dart` falls into exactly one of two buckets: `core/` (shared
infrastructure) or `features/` (one folder per vertical slice of the product).

```
my_app/
├── lib/
│   ├── main.dart                # ~3 lines: calls bootstrap(), nothing else
│   ├── bootstrap.dart           # async startup sequence, error zone, runApp()
│   ├── app/
│   │   └── app.dart             # the root MaterialApp widget + theming + route-to-home logic
│   ├── core/
│   │   ├── config/              # environment/base-URL resolution, static app-wide constants
│   │   ├── network/             # ApiClient, ApiException, token-refresh, auth-status guards
│   │   ├── storage/              # TokenStorage (secure), LocalDatabase (sqflite), small
│   │   │                        #   ChangeNotifier/singleton preference stores
│   │   ├── sync/                 # SyncManager: push/pull orchestration against the local DB
│   │   ├── connectivity/         # online/offline detection service
│   │   ├── navigation/           # a global NavigatorState key for navigation without context
│   │   ├── theme/                # ThemeData construction, app-wide color/theme state
│   │   ├── widgets/               # generic, feature-agnostic reusable widgets (dialogs,
│   │   │                          #   banners, form sections, pickers, status badges)
│   │   └── utils/                 # pure functions: formatters, validators, small parsers
│   └── features/
│       └── <feature_name>/        # one per vertical slice, e.g. customers, orders, products
│           ├── data/
│           │   ├── models/        # plain Dart data classes (fromJson/toJson), no logic
│           │   └── <feature>_repository.dart
│           └── presentation/
│               ├── <feature>_page.dart         # top-level screen(s) for this feature
│               └── widgets/                     # widgets used only within this feature
├── assets/
│   ├── icon/  fonts/  onboarding/  sounds/      # whatever static assets the app ships
├── test/                                        # flat list of *_test.dart files, one per unit
├── android/  ios/                                # platform runners (generated by `flutter create`)
├── analysis_options.yaml
└── pubspec.yaml
```

**One-line purpose of each top-level folder:**

| Folder | Purpose |
|---|---|
| `lib/main.dart` | Entry point only — delegates immediately to `bootstrap()`. Kept empty on purpose so there is exactly one place startup logic can live. |
| `lib/bootstrap.dart` | Everything that must happen before `runApp()`: load persisted state, init date formatting, wrap in a guarded error zone, kick off background sync. |
| `lib/app/` | The `MaterialApp` widget itself: theme, locale, routing-to-home decision tree. Deliberately separate from `bootstrap.dart` so app-shell concerns (theme, locale) don't mix with startup-sequencing concerns. |
| `lib/core/` | Anything more than one feature needs. If only one feature ever imports it, it does not belong here. |
| `lib/features/` | One folder per vertical slice of product functionality. A feature folder is a bounded context: it may import `core/`, but other features should reach into it only through its `data/` repository, never its `presentation/` internals. |
| `assets/` | Static files declared in `pubspec.yaml`'s `flutter: assets:` section. |
| `test/` | Flat, not mirrored to `lib/`'s tree — one file per behavior under test, named for what it tests (`invoice_edit_test.dart`), not for which class it tests. |

## 2. The `core/` vs `features/` split

**Rule of thumb used throughout this codebase:** if a second feature would need to import it, it
belongs in `core/`. If it only makes sense in the context of one feature's business concept, it
stays inside that feature's folder. This project draws the line concretely as:

**Lives in `core/` (this project's actual contents, generalized):**
- The single HTTP client wrapper (`core/network/api_client.dart`) — every feature's repository
  constructs its own `ApiClient` instance, but they all share the same class and the same
  auth/retry/error-mapping behavior.
- The local database singleton (`core/storage/local_database.dart`) — one `sqflite` handle, one
  schema, one migration ladder, shared by every feature's repository.
- Secure-storage-backed session state (`core/storage/token_storage.dart`,
  `core/storage/session_status.dart`) — auth is cross-cutting, not feature-specific.
- Small `ChangeNotifier` singletons for app-wide, persisted UI preferences (theme, language,
  design mode) — `core/theme/app_theme.dart`, `core/storage/app_language.dart`.
- Generic, visually-reusable widgets with no business meaning: `core/widgets/modal_page_sheet.dart`,
  `core/widgets/searchable_picker.dart`, `core/widgets/status_ring.dart`, `core/widgets/app_notice.dart`.
- Pure utility functions: `core/utils/formatters.dart`, `core/utils/phone_validator.dart`,
  `core/utils/decimal_input_formatter.dart`.
- Cross-cutting infrastructure with its own internal complexity that no single feature owns:
  `core/sync/sync_manager.dart` (generic push/pull orchestration), `core/connectivity/connectivity_service.dart`.

**Lives inside a feature folder (using `features/customers/` as the concrete example read from source):**
```
features/customers/
├── data/
│   ├── models/
│   │   └── customer.dart                   # plain data class: fields + fromJson factory
│   ├── customers_repository.dart           # the ONLY class that touches the customers
│   │                                        #   SQLite table or calls /customers endpoints
│   └── customer_statement_pdf_builder.dart # feature-specific derived artifact (a PDF), not
│                                            #   reusable anywhere else
└── presentation/
    └── clients_page.dart                   # the screen; feature-local widgets that would
                                             #   only ever appear here live in a
                                             #   presentation/widgets/ subfolder (see
                                             #   features/orders/presentation/widgets/ for
                                             #   the pattern with more than one screen)
```

**Is there a domain layer? No — this is deliberately a two-layer split, not Clean
Architecture's three (`data` / `domain` / `presentation`).** There is no separate `UseCase`/
`Interactor` class per operation, and no repository *interface* abstracted away from its
implementation — `CustomersRepository` is a concrete class that presentation code instantiates
and calls directly (`final _repository = CustomersRepository();` inside the page's `State`).

Why this fits a small-to-medium app better than three-layer Clean Architecture:
- **The repository already *is* the use-case boundary.** Its public methods
  (`getAll`, `getPageLocal`, `create`, `update`, `delete`, `sync`) each encapsulate one complete
  business operation (e.g. `delete` is documented in source as "soft delete, matching the
  backend's `IsActive`-based sync protocol" — that *is* the use case, not a thin CRUD passthrough).
  Adding a `DeleteCustomerUseCase` wrapper around a one-method call to
  `CustomersRepository.delete()` would be an abstraction with no second implementation and no
  second caller — pure ceremony.
- **There is exactly one implementation of each repository**, and it will realistically stay that
  way (there's no plan to swap SQLite for another local store, or the REST API for GraphQL).
  Interface/implementation separation earns its cost when a second implementation is either
  planned or needed for testing with fakes; neither applies here, so `CustomersRepository` is a
  concrete class, not `ICustomersRepository` + `SqliteCustomersRepository`.
- **Models are plain data, not entities-with-behavior.** `Customer` is a `const` class with a
  `fromJson` factory and nothing else — there's no domain-layer "business object" distinct from
  the data-layer DTO, because the two would be structurally identical here.

**When would three layers be justified instead?** If a single business rule needed to be reused
across multiple repositories/data sources, or the team needed to unit-test business logic with
the data layer entirely mocked out via interfaces, promoting to interfaces + use-case classes
would pay for itself. Until then, the two-layer split is the right default — it is less code,
equally testable (repositories are already unit-tested directly against a real in-memory/test
SQLite database — see the `-j 1` note on test running in the CI/dev process), and every engineer
touching a feature only has to learn one place logic lives.

## 3. State management choice

**Confirmed from `pubspec.yaml`: there is no `provider`, `flutter_riverpod`, `flutter_bloc`, or
similar package listed anywhere in `dependencies`.** State management is:

1. **`StatefulWidget` + `setState`** for everything screen-local (loading flags, form fields,
   pagination cursors, selection sets).
2. **Bare `ChangeNotifier` singletons** (not registered with any DI/provider framework — just a
   static `instance` field) for state that must be *visible app-wide* and trigger a rebuild in
   places other than the widget that changed it. Example, read verbatim from source
   (`core/theme/app_theme.dart`):

   ```dart
   /// A [ChangeNotifier] rather than a plain singleton (contrast
   /// [InvoicePreferences]) because [FatoraApp] listens to it directly so every
   /// screen re-themes immediately when the user changes either setting in
   /// Appearance settings, instead of only the page that changed it.
   class AppTheme extends ChangeNotifier {
     AppTheme._();
     static final instance = AppTheme._();
     ThemeMode mode = ThemeMode.light;
     int accentValue = _defaultAccent;
     Future<void> setMode(ThemeMode value) async {
       mode = value;
       notifyListeners();
       await _storage.write(key: _modeKey, value: value.name);
     }
   }
   ```
   Consumed with Flutter's own `ListenableBuilder` at the app root — no external package needed:
   ```dart
   ListenableBuilder(
     listenable: Listenable.merge([AppTheme.instance, AppLanguage.instance]),
     builder: (context, child) => MaterialApp(theme: _theme(Brightness.light), ...),
   )
   ```
3. **A bare `ValueNotifier<int>` "cache signal" singleton** for the narrower problem of "tell
   other already-open screens that this feature's cached data changed." Read verbatim
   (`features/orders/data/orders_cache_signal.dart`):
   ```dart
   /// Bumped whenever an order changes anywhere ... [InvoicesPage] and a
   /// customer's own invoice history listen for this to know their
   /// already-loaded list is stale ... without the user having to leave and
   /// reopen the page.
   class OrdersCacheSignal {
     OrdersCacheSignal._();
     static final instance = OrdersCacheSignal._();
     final version = ValueNotifier<int>(0);
     void invalidate() => version.value++;
   }
   ```
   A page that cares wraps part of its `build()` in a `ValueListenableBuilder` on
   `OrdersCacheSignal.instance.version` instead of subscribing to a stream or a provider tree.

   Preferences that are read-mostly and don't need to trigger a rebuild elsewhere (e.g.
   `InvoicePreferences`) skip `ChangeNotifier` entirely and are just a plain singleton class with
   a `load()`/getters — no notification machinery at all. **The rule observed: reach for
   `ChangeNotifier`/`ValueNotifier` only when something *outside* the widget that owns the state
   needs to react to it; otherwise a plain class or local `setState` is enough.**

**The load/spinner/error/data pattern for a page with async data** (read verbatim from
`features/customers/presentation/clients_page.dart`, generalizable to any paginated list):

```dart
class _ClientsPageState extends State<ClientsPage> {
  final _repository = CustomersRepository();
  List<Customer> _clients = [];
  bool _initialLoading = true;
  Object? _loadError;

  @override
  void initState() {
    super.initState();
    _loadFirstPage();       // show whatever's already cached locally, instantly
    _syncThenReload();      // then sync in the background and silently refresh
  }

  Future<void> _loadFirstPage() async {
    setState(() { _initialLoading = true; _loadError = null; });
    try {
      final page = await _repository.getPageLocal(skip: 0, take: _pageSize);
      if (!mounted) return;
      setState(() { _clients = page; _initialLoading = false; });
    } catch (e) {
      if (!mounted) return;
      setState(() { _loadError = e; _initialLoading = false; });
    }
  }
  // ...
  // in build():
  if (_initialLoading && _clients.isEmpty)
    const Center(child: CircularProgressIndicator())
  else if (_loadError != null && _clients.isEmpty)
    _ErrorState(
      message: _loadError is ApiException ? (_loadError! as ApiException).message : 'تعذّر تحميل العملاء.',
      onRetry: _reload,
    )
  else if (rows.isEmpty)
    const _EmptyState()
  else
    /* the list */
}
```

The pattern's key properties, worth adopting as-is in a new project:
- **Local-cache-first, not network-first.** The first paint always comes from local storage
  (instant, works offline); the network sync is a *second*, silent step that only updates state
  `if (!mounted)`-guarded and only on success — a failed background sync never clobbers a
  successfully-loaded cached list with an error screen.
- **Three explicit booleans/nullable-object, not a sealed "AsyncValue" union type**:
  `_initialLoading`, `_loadError` (an `Object?`, not a typed exception — cheaper to plumb, and
  the UI only ever needs `.toString()`-equivalent behavior via `ApiException.message`), and the
  data list itself, whose emptiness is the third state. This is 3 fields per page, duplicated
  per page, rather than a shared generic wrapper — an intentional trade favoring simplicity over
  DRY for something this small (see YAGNI in the project's own engineering guidelines).
- `if (!mounted) return;` is checked after every `await` before calling `setState`, unconditionally.

## 4. Networking layer

**One shared `ApiClient` class** (`core/network/api_client.dart`), constructed fresh by each
repository (`ApiClient({http.Client? httpClient, TokenStorage? tokenStorage})`), wrapping the
`http` package. Its public surface is deliberately small and uniform:

```dart
Future<dynamic> get(String path, {bool auth = false});
Future<dynamic> post(String path, {Map<String, dynamic>? body, bool auth = false});
Future<dynamic> put(String path, {Map<String, dynamic>? body, bool auth = false});
Future<dynamic> delete(String path, {Map<String, dynamic>? body, bool auth = false});
Future<dynamic> uploadImage(String path, String filePath);
Future<Uint8List> getBytes(String path, {bool auth = false});   // for raw file downloads (PDF/CSV)
```

**How it attaches the auth token:** `auth: true` on any call makes it read the access token from
`TokenStorage` and set `Authorization: Bearer <token>` before sending. Callers opt in per-call
rather than the client always attaching a token — this makes anonymous endpoints (login, register)
explicit at the call site instead of relying on a token being absent.

**How it maps HTTP errors to a typed exception:** every non-2xx response — and every network-level
failure (`SocketException`, `HttpException`, `TimeoutException`) — is converted into a single typed
exception, never left as a raw `http.Response` or a generic `Exception`:

```dart
class ApiException implements Exception {
  const ApiException(this.message, {this.statusCode, this.code});
  final String message;
  final int? statusCode;
  final String? code;          // machine-readable discriminator for specific server-side error codes
  bool get isOffline => statusCode == null;   // true only for connection-never-reached failures
}
```

Every screen displays `ApiException.message` directly — this is the **one and only place** that
turns `(statusCode, decoded-JSON-body)` into a human-readable string, so message copy/localization
lives in exactly one file, not scattered through every repository or page:

```dart
String _errorMessage(int statusCode, dynamic decoded) {
  final serverMessage = _extractServerMessage(decoded);   // prefer the server's own message/detail
  if (serverMessage != null) return serverMessage;
  if (statusCode == 400) return 'البيانات المدخلة غير صحيحة...';
  if (statusCode == 401) return 'انتهت صلاحية الجلسة...';
  if (statusCode == 403) return 'ليس لديك صلاحية...';
  if (statusCode == 429) return 'محاولات كثيرة خلال وقت قصير...';
  if (statusCode >= 500) return 'حدث خطأ في الخادم...';
  return 'حدث خطأ غير متوقع (رمز $statusCode).';
}
```

**Other production-grade behaviors worth copying wholesale into a new project's `ApiClient`:**
- **Silent one-shot retry on transient failures** (offline-but-really-just-slow, or 502/503/504
  from a cold-starting free-tier host) — never retries when the device is confirmed offline
  (checked against a `ConnectivityService`), since that would just be a pointless extra wait.
- **Coalesced token refresh**: a `static Future<bool>? _refreshInFlight` field ensures that if two
  requests get a 401 at the same moment, only one actually calls the refresh endpoint; the second
  awaits the first's in-flight `Future` instead of triggering a duplicate rotation (which would
  invalidate the first request's freshly-rotated token out from under it).
- **Decode the body as UTF-8 explicitly from `bodyBytes`**, never via `response.body` — the latter
  silently falls back to Latin-1 when a response omits a charset, garbling any non-ASCII text.
- The client never throws on a decode of an empty body; `''` maps to `null`, not a `FormatException`.

## 5. Local storage choices

Three different local-storage mechanisms, each picked for a distinct shape of data — **do not use
one tool for all three jobs**:

| Mechanism | Package | Used for | Why |
|---|---|---|---|
| **Structured relational cache** | `sqflite: ^2.4.2` (+ `sqflite_common_ffi` as a dev-only dependency for running DB-touching tests on desktop/CI) | The full offline mirror of every syncable server entity — customers, products, orders, order line items — each as a real SQL table with a `dirty INTEGER` flag and typed columns. | This data is genuinely relational (orders have line items with foreign keys), is queried with `WHERE`/`ORDER BY`/`LIMIT`/`OFFSET` for pagination and filtering (see `CustomersRepository.getPageLocal`), and needs a real schema migration path (`openDatabase(path, version: 25, onCreate: ..., onUpgrade: ...)`) as the entity shape evolves release over release. A key-value or document store would make every list/filter/paginate query into manual in-memory work. |
| **Secrets** | `flutter_secure_storage: ^10.3.1` | JWT access/refresh tokens, the last-known-good login QR payload — anything that must live in the OS keystore/keychain, not a plain file. | The only thing in this codebase that qualifies as a genuine secret. Everything else that merely *looks* sensitive (usernames, cached account id used to detect an account switch) also happens to live here for convenience, but the deciding factor is "would leaking this file matter" — the token pair is the one thing that would. |
| **Simple app-wide preferences/flags** | **Also `flutter_secure_storage`**, wrapped in small singleton classes (`AppTheme`, `AppLanguage`, `OnboardingStatus`, `SessionStatus`, `ImportTutorialStatus`, ...) — **not `shared_preferences`**, which is not a dependency in `pubspec.yaml` at all. | Theme mode/accent, locale, "has onboarding been completed," "has this one-time tutorial been shown," printer preferences. | This project made a deliberate simplification: rather than adding a second key-value package for non-secret flags, it reuses `flutter_secure_storage` for everything key-value-shaped, secret or not. **This is a defensible but non-default choice** — a new project with no other reason to standardize on secure storage should default to `shared_preferences` for genuinely non-sensitive flags (faster, no platform-channel/keystore round-trip cost) and reserve `flutter_secure_storage` for actual secrets. Note the concrete cost this project pays for its choice: `bootstrap.dart`'s own comment explains why ~13 of these stores are all awaited together via `Future.wait` rather than sequentially — "each of these is an independent read from secure storage (a real platform-channel + Keystore round trip, not free)." A `shared_preferences`-backed store avoids that cost entirely for data that was never secret to begin with. |

**No Hive, no Isar, no Drift/Moor.** `sqflite` was chosen directly over a higher-level ORM/reactive
database — there is no code-generation step, no reactive-query layer; repositories hand-write SQL
via `db.query(...)`/`db.insert(...)`/`db.transaction(...)`. This keeps the storage layer legible
without a build_runner step, at the cost of writing `_rowToCustomer`/`_customerToRow` mapping
functions by hand per entity — an acceptable trade for a schema of this size (order of ten tables).

## 6. ASP.NET solution skeleton

*(For the full architectural rationale — layering, multi-tenancy, exception hierarchy, sync
protocol — see this project's own `README.md`; this section is only "how do I lay out a new
solution to start," not a duplicate of that content.)*

Three projects, one `.sln`/`.slnx`, a strict one-way reference chain:

```
MyApp.slnx
├── MyApp.API/            →  MyApp.BL.csproj                (only reference)
│   ├── Controllers/
│   ├── Validators/<Domain>Validators/
│   ├── Services/          (API-layer infra only, e.g. file storage — NOT business services)
│   ├── Extensions/         (ClaimsPrincipal helpers, etc.)
│   ├── Exceptions/          GlobalExceptionHandler.cs
│   ├── Filters/
│   ├── GroupRegistrations.cs    (all DI registrations, one file)
│   ├── Program.cs
│   ├── appsettings.json          (committed — no secrets)
│   └── appsettings.Development.json  (gitignored — local secrets only)
├── MyApp.BL/               →  MyApp.DAL.csproj              (only reference)
│   ├── Services/
│   │   ├── Abstractions/    (interfaces: I<Name>Service)
│   │   └── Classes/          (implementations: <Name>Service)
│   ├── DTOs/
│   │   ├── Requests/
│   │   └── Responses/
│   ├── Exceptions/            AppException hierarchy
│   └── Utils/
└── MyApp.DAL/                →  no project references (leaf project)
    ├── Entites/                 (EF Core entity classes)
    └── Data/
        ├── AppDbContext.cs
        ├── Configuration/        (IEntityTypeConfiguration<T>, one file per entity)
        └── Migrations/
```

**Reference direction is one-way and enforced by which `.csproj` has a `<ProjectReference>` to
which:** `API → BL → DAL`. `MyApp.DAL.csproj` has zero `ProjectReference` entries — it is a leaf.
`MyApp.API.csproj` references *only* `MyApp.BL.csproj` (it never references `DAL` directly — a
controller cannot see `AppDbContext` or any entity type, only DTOs and service interfaces). This
is the mechanism, not just a convention: the reference graph itself makes a layering violation a
compile error, not a code-review catch.

**Target framework and core package split**, confirmed from the actual `.csproj` files:
- All three projects target the same `<TargetFramework>` (`net10.0` here — use whatever current
  LTS/STS applies to a new project) with `<Nullable>enable</Nullable>` and
  `<ImplicitUsings>enable</ImplicitUsings>` uniformly.
- `MyApp.API.csproj` (`Sdk="Microsoft.NET.Sdk.Web"`) — the only project on the **Web** SDK — holds
  `Microsoft.AspNetCore.OpenApi`, EF Core's design-time tooling package
  (`Microsoft.EntityFrameworkCore.Design`, `PrivateAssets="all"` since it's build-only), plus
  whatever cross-cutting API packages the app needs (this project: `CloudinaryDotNet`,
  `FluentValidation.AspNetCore`).
- `MyApp.BL.csproj` (`Sdk="Microsoft.NET.Sdk"`) holds business-facing packages that don't need
  ASP.NET hosting: `FluentValidation.DependencyInjectionExtensions`,
  `Microsoft.Extensions.Identity.Core` (for `PasswordHasher<T>` without pulling in full ASP.NET
  Identity).
- `MyApp.DAL.csproj` (`Sdk="Microsoft.NET.Sdk"`) holds only data-access packages:
  `Microsoft.EntityFrameworkCore`, the specific provider (`Npgsql.EntityFrameworkCore.PostgreSQL`
  here), and `Microsoft.AspNetCore.Authentication.JwtBearer` (needed here only because a couple of
  DAL-level concerns reference JWT claim types — evaluate whether your own DAL genuinely needs an
  auth package reference before copying this one).

## 7. Program.cs / startup wiring

The shape to replicate, in order, confirmed from the real `Program.cs`:

**1. Build + register services** (before `builder.Build()`):
```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddOpenApi();
builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();

builder.Services.AddGroupedServices();   // one extension method, defined in GroupRegistrations.cs,
                                          // registering every I<X>Service -> <X>Service pair and
                                          // every FluentValidation validator as Scoped

var connectionString = builder.Configuration.GetConnectionString("DefaultConnection");
if (string.IsNullOrEmpty(connectionString))
    throw new InvalidOperationException("ConnectionStrings:DefaultConnection is not configured. " +
        "Set it in appsettings.Development.json locally, or the ConnectionStrings__DefaultConnection " +
        "environment variable in production.");
builder.Services.AddDbContext<AppDbContext>(options => options.UseNpgsql(connectionString));

builder.Services.AddAuthentication(...).AddJwtBearer(options => { /* reads JwtSettings:SecretKey,
    throws its own clear InvalidOperationException if missing, exactly like the connection string */ });
builder.Services.AddAuthorization();
builder.Services.AddRateLimiter(options => { /* named policies per sensitive endpoint, see below */ });
builder.Services.AddControllers(options => options.Filters.Add<AccountStatusFilter>())
    .AddJsonOptions(o => o.JsonSerializerOptions.Converters.Add(new JsonStringEnumConverter()));
```

**Fail-fast configuration validation is a deliberate, repeated pattern**: both the DB connection
string and the JWT secret key throw an explicit, named `InvalidOperationException` at startup —
naming exactly which config key is missing and where it should come from — rather than letting a
missing value surface later as a confusing null-reference deep in a request handler. Copy this
pattern for every required secret in a new project.

**2. Build the app, run startup-time database work, in a scoped block:**
```csharp
var app = builder.Build();

using (var scope = app.Services.CreateScope())
{
    var services = scope.ServiceProvider;
    var dbContext = services.GetRequiredService<AppDbContext>();
    await dbContext.Database.MigrateAsync();          // migrations apply automatically on boot
    await SeedData.seedAuthDataAysnc(services);        // roles + a seeded admin/owner account
}
```
This makes every deploy self-migrating — no separate manual migration step in the deploy process.
(Trade-off worth naming explicitly to whoever inherits this: automatic migration-on-boot is
convenient for a small team on a single-instance PaaS deploy; it becomes a liability the moment
there are multiple instances starting concurrently or a migration needs a manual data-backfill
step first. Fine for the scale this project runs at; reconsider before scaling out.)

**3. Middleware pipeline, in this exact order — order is called out as load-bearing in the
source comments themselves:**
```csharp
app.UseForwardedHeaders(forwardedHeadersOptions);  // MUST be first: resolves the real client IP
                                                    // from X-Forwarded-For behind a PaaS edge proxy
app.UseRouting();                                  // MUST precede UseRateLimiter: the limiter needs
                                                    // endpoint metadata resolved to apply per-route
                                                    // [EnableRateLimiting] policies
app.UseRateLimiter();

if (app.Environment.IsDevelopment()) app.MapOpenApi();
else app.UseHttpsRedirection();   // only outside Development — mobile clients hit a local dev
                                   // server over plain HTTP; redirecting to HTTPS there breaks them

app.UseStaticFiles();
app.UseExceptionHandler();        // pairs with AddExceptionHandler<GlobalExceptionHandler> above
app.UseStatusCodePages();

app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.MapGet("/health", () => Results.Ok(new { Message = "all up" }));   // for PaaS health checks
app.Run();
```

**Configuration loading — `appsettings.json` shape** (values redacted; structure only):
```jsonc
// appsettings.json — committed, contains NO secrets, safe to share
{
  "Logging": { "LogLevel": { "Default": "Information", "Microsoft.AspNetCore": "Warning" } },
  "AllowedHosts": "*",
  "JwtSettings": { "Issuer": "...", "Audience": "...", "TokenExpirationInMinutes": 10 },
  "AdminSeed": { "UserName": "..." },
  "AdminRecovery": { "Email": "..." }
}
```
```jsonc
// appsettings.Development.json — gitignored, local secrets only, loaded automatically by `dotnet run`
{
  "Logging": { ... },
  "ConnectionStrings": { "DefaultConnection": "Host=...;Password=..." },
  "JwtSettings": { "SecretKey": "..." },
  "AdminSeed": { "Password": "..." },
  "SMTP_PASSWORD": "...",
  "CLOUDINARY_CLOUD_NAME": "...", "CLOUDINARY_API_KEY": "...", "CLOUDINARY_API_SECRET": "..."
}
```

**The rule this split encodes**: `appsettings.json` holds every key whose *presence* is not
sensitive (an issuer name, a seeded username, a non-secret recovery email address) — this file is
committed and safe to read by anyone with repo access. Anything whose *value* is sensitive (a
connection string with an embedded password, a JWT signing key, an SMTP password, API secrets)
lives only in `appsettings.Development.json`, which is listed in `.gitignore` explicitly (with a
comment pointing back at where the production equivalent lives) — **never committed, not even for
a "throwaway" local value**. In production/deployment, the same sensitive keys are supplied purely
as environment variables using ASP.NET's `Section__Key` double-underscore convention
(`ConnectionStrings__DefaultConnection`, `JwtSettings__SecretKey`, `AdminSeed__Password`) — nothing
sensitive ever lives in a file at all outside local dev.

## 8. Naming and file-organization conventions

Consistent, mechanical naming patterns observed across both codebases — adopt these from the
first file written, not retrofitted later:

**Backend:**
- Every business service is a pair: `I<Name>Service` interface in `Services/Abstractions/`, and
  `<Name>Service` implementation in `Services/Classes/` (e.g. `ICustomerService` / `CustomerService`,
  `IOrderService` / `OrderService`). No exceptions observed — every one of the ~23 services in
  `GroupRegistrations.cs` follows this, registered `AddScoped<IXxxService, XxxService>()`.
  Note: this pairing is only applied to `BL` services — the two-layer Flutter side deliberately
  skips this same interface/impl split for repositories (see §2) because repositories there have
  exactly one implementation and no test-substitution need; the backend keeps it because
  `IXxxService` doubles as the DI-registered contract every controller actually depends on.
- Every EF Core entity has exactly one matching `<Entity>Configuration : IEntityTypeConfiguration<Entity>`
  file in `Data/Configuration/` (e.g. `CustomerConfiguration`, `OrderConfiguration`,
  `RepCustomerAccessConfiguration`) — one file per entity, never multiple entities configured in
  one file, never entity configuration inlined in `AppDbContext.OnModelCreating`.
- DTOs are split by direction, not by entity: `DTOs/Requests/<Verb><Entity>Request.cs`
  (`CreateCustomerRequest`, `UpdateCustomerRequest`, `RecordPaymentRequest`) and
  `DTOs/Responses/`. A request DTO is never reused as a response shape or vice versa.
- Validators are `<RequestName>Validator` (e.g. `CreateCustomerRequestValidator`), grouped into
  one subfolder per domain under `Validators/` (`Validators/CustomerValidators/`,
  `Validators/OrderValidators/`), registered `AddScoped<XxxValidator>()` (concrete class, not an
  interface — FluentValidation validators are consumed directly, not through DI abstraction).
- Custom exceptions all derive from one `AppException` base (`NotFoundException`,
  `ConflictException`, `UnauthorizedException`, `ForbiddenException`, `BadRequestException`) —
  named for the HTTP semantics they map to, caught in exactly one place (`GlobalExceptionHandler`).
- Controllers are thin: `[HttpVerb]` action → validate → call one service method → return. No
  controller in this codebase contains a `try/catch` — all error mapping happens centrally.

**Frontend:**
- Every feature's data-access class is `<Feature>Repository` (`CustomersRepository`,
  `OrdersRepository`, `ProductsRepository`), always in `features/<feature>/data/`, always the
  single point of contact between `presentation/` and both SQLite and the network for that
  feature.
- Every feature's model is a bare noun (`Customer`, `Order`, `Product`) in
  `features/<feature>/data/models/`, with a `factory <Model>.fromJson(Map<String, dynamic> json)`
  and no `toJson` unless the model is actually sent back to the server as-is (repositories here
  hand-build request maps instead — see `_customerToRow`/`_send(body: {...})` patterns — rather
  than a symmetrical `toJson`).
- Every top-level screen is `<Noun>Page` (`ClientsPage`, `InvoicesPage`, `ItemsPage`), its private
  `State` class is `_<Noun>PageState`, and screen-local widgets that don't need to be public live
  as private (`_ErrorState`, `_EmptyState`) classes at the bottom of the same file; only widgets
  actually reused across more than one file in the feature get promoted to
  `presentation/widgets/`.
- Singletons (whether a `ChangeNotifier`, a `ValueNotifier` wrapper, or a plain class) follow one
  constructor idiom throughout: a private named constructor plus a static `instance` field —
  `ClassName._(); static final instance = ClassName._();` — never a bare top-level global variable.
- API error type is always `ApiException`, always caught explicitly and distinguished from other
  exceptions (`on ApiException catch (e)`), never a bare `catch (e)` that would also swallow
  programming errors.

## 9. Day-one checklist

### Flutter frontend — first 10–15 steps, before any real feature

1. `flutter create` the project; delete the default demo counter code from `main.dart` and the
   generated test.
2. Create the empty `lib/core/` and `lib/features/` folders (§1) — commit them with a `.gitkeep`
   or the first real file, so the split exists before anyone is tempted to dump a file at
   `lib/` root.
3. Add `analysis_options.yaml` extending `package:flutter_lints/flutter.yaml`, and turn on at
   least: `always_declare_return_types`, `avoid_print`, `prefer_final_locals`,
   `unawaited_futures`, `directives_ordering`. Promote `missing_required_param` and
   `missing_return` from warning to `error` under `analyzer: errors:`.
4. Add core dependencies to `pubspec.yaml` and justify each by category before adding it:
   `http` (networking), `flutter_secure_storage` (secrets/tokens), `sqflite` + `path` (local
   relational cache) if the app needs offline data, `connectivity_plus` (online/offline
   detection), `intl` (formatting/dates), `uuid` (client-generated ids for offline-created
   records), `package_info_plus` (app version display/reporting).
5. Write `core/network/api_client.dart` first, before any feature — a single `ApiClient` class
   with `get/post/put/delete`, an `auth` flag per call, and everything decoded through one
   `_decode` method that throws one `ApiException` type (§4). Every later repository depends on
   this existing already.
6. Write `core/network/api_exception.dart` — the typed exception with `message`, `statusCode`,
   `isOffline`, and an optional machine-readable `code`.
7. Write `core/storage/token_storage.dart` wrapping `flutter_secure_storage`, with
   `saveSession`/`readAccessToken`/`readRefreshToken`/`clear` — decide up front whether you need
   JWT-claim reading (`readRole`, `readSubject`) baked in here.
8. If the app needs offline data: write `core/storage/local_database.dart` as a single
   `LocalDatabase` singleton wrapping `sqflite`, with `onCreate`/`onUpgrade` from day one even
   with only one table — the migration ladder is much cheaper to start now than to retrofit
   after the first schema change ships to real users.
9. Write `core/config/app_config.dart` to resolve the API base URL — at minimum, a distinct
   value for a debug build (pointing at localhost/emulator alias) versus a release build
   (pointing at the deployed backend), gated on `kReleaseMode`.
10. Write `bootstrap.dart`: wrap startup in `runZonedGuarded`, call
    `WidgetsFlutterBinding.ensureInitialized()`, load every persisted preference/status singleton
    via one `Future.wait([...])` (not sequential awaits — see §1's `bootstrap.dart` example), then
    `runApp()`.
11. Write `app/app.dart`: the root `MaterialApp`, theme construction, and the
    `_resolveHome()`-style decision tree (onboarding → login → main app) as one method, not
    scattered across widgets.
12. Pick the state-management default explicitly and write it down (even if the answer is "plain
    `setState` + `ChangeNotifier` singletons for cross-screen state, no package") before the
    second feature is built, so every subsequent feature is consistent from the start.
13. Build the *first* feature folder end-to-end (`data/models/`, `data/<feature>_repository.dart`,
    `presentation/<feature>_page.dart`) as the template every later feature copies — get this one
    right, since it becomes the pattern by imitation.
14. Set up `test/` as a flat folder and write one smoke test against the first repository before
    moving to the second feature, to lock in the local-database test setup (in-memory or
    `sqflite_common_ffi` for desktop/CI test runs) early.

### ASP.NET backend — first 10–15 steps, before any real feature

1. Create the solution and three projects with `dotnet new`: `dotnet new sln`, then
   `dotnet new webapi -o MyApp.API`, `dotnet new classlib -o MyApp.BL`,
   `dotnet new classlib -o MyApp.DAL`; add all three to the `.sln`/`.slnx`.
2. Wire the one-way reference chain immediately: `dotnet add MyApp.API reference MyApp.BL`,
   `dotnet add MyApp.BL reference MyApp.DAL` — and *only* those two references. Never add
   `MyApp.API → MyApp.DAL` directly, even as a shortcut.
3. Set `<TargetFramework>`, `<Nullable>enable</Nullable>`, `<ImplicitUsings>enable</ImplicitUsings>`
   identically in all three `.csproj` files.
4. Install EF Core + your database provider into `MyApp.DAL` only
   (`Microsoft.EntityFrameworkCore` + e.g. `Npgsql.EntityFrameworkCore.PostgreSQL`); install
   `Microsoft.EntityFrameworkCore.Design` into `MyApp.API` only (design-time tooling belongs at
   the startup project, `PrivateAssets="all"`).
5. Create `MyApp.DAL/Data/AppDbContext.cs` and an empty `Data/Configuration/` folder; add your
   first `IEntityTypeConfiguration<T>` file the moment your first entity exists — never inline
   configuration into `OnModelCreating` as a shortcut.
6. Create the `Exceptions/` folder in `MyApp.BL` with the base `AppException` and its first two or
   three HTTP-semantic subclasses (`NotFoundException`, `BadRequestException`,
   `ConflictException`) before writing the first service — every service method that can fail
   needs somewhere typed to throw into immediately.
7. Create `MyApp.API/Exceptions/GlobalExceptionHandler.cs` implementing `IExceptionHandler`,
   mapping the `AppException` hierarchy to `ProblemDetails`, registered via
   `AddExceptionHandler<GlobalExceptionHandler>()` + `AddProblemDetails()` — wire this before the
   first controller exists, so no controller is ever tempted to add its own `try/catch`.
8. Create `MyApp.API/GroupRegistrations.cs` as the single file where every
   `AddScoped<IXxxService, XxxService>()` and every validator registration happens — start it
   empty and add one pair per service as you build it, never register a service inline in
   `Program.cs`.
9. Write `Program.cs`'s configuration-and-fail-fast section first: read the connection string and
   any signing secret from `builder.Configuration`, and `throw new InvalidOperationException`
   with a specific, actionable message if either is missing, before wiring anything that depends
   on them.
10. Set up the `appsettings.json` / `appsettings.Development.json` split (§7) on day one: add
    `appsettings.Development.json` to `.gitignore` with a comment explaining why, and put a
    placeholder/example of its required shape in the README instead — never let a real secret
    land in the committed file even temporarily.
11. Wire the middleware pipeline in `Program.cs` in the order given in §7 — forwarded headers,
    then routing, then rate limiting, then the environment-gated OpenAPI/HTTPS-redirect branch,
    then exception/status-code handling, then auth, then `MapControllers()` — and add a
    `MapGet("/health", ...)` endpoint immediately, since your deploy platform's health check
    depends on it existing before the first real deploy.
12. Decide the migration strategy explicitly before the first entity ships: this project runs
    `dbContext.Database.MigrateAsync()` automatically inside a startup scope on every boot —
    a deliberate choice appropriate for a single-instance PaaS deployment (see the caveat in §7)
    — write down whether that's still the right call for your deployment topology before copying it.
13. Add a `Utils/SeedData.cs`-equivalent if the app needs a seeded initial account/role — call it
    from the same startup scope, right after migrations, and read its password only from an
    environment variable, never a default committed anywhere.
14. Create your first domain vertical end-to-end — one entity, one `IEntityTypeConfiguration`,
    one `I<Name>Service`/`<Name>Service` pair, one controller, one pair of request DTOs, one
    validator — as the template every later feature copies, following the naming conventions in §8.
15. Write a professional `README.md` early (Tech Stack, Architecture diagram, Project Structure
    tree, Getting Started, Deployment/environment-variables table) — this project's own `README.md`
    is itself the best evidence that documenting the layering rule in prose, next to the code that
    enforces it via `ProjectReference`, keeps the two from drifting apart.
